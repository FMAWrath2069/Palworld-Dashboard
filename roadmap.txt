# Palworld Admin Dashboard

## Project Handoff / Current State

**Last Updated:** July 2026

---

# Project Overview

This project is a **web-based Palworld Dedicated Server administration dashboard**.

The goal is to provide a clean, modern administration interface that communicates with a backend REST API and exposes nearly every server management function through the browser.

This is **not** intended to be a public player-facing website.

Every feature is considered an administrator command.

---

# Current Architecture

The frontend has recently been reorganized into feature-specific modules.

```
js/
│
├── main.js                 // App bootstrap only
│
├── services/
│   ├── api.js
│   ├── map.js
│   ├── modal.js
│   ├── server.js
│   └── storage.js
│
├── modules/
│   ├── events.js
│   ├── refresh.js
│   ├── players.js
│   ├── logs.js
│   ├── actions.js
│   ├── configuration.js
│   └── utils.js
```

The goal is that **main.js remains a lightweight application bootstrap.**

---

# Module Responsibilities

## main.js

Contains only:

* App state
* initialization
* startup

Should never contain feature implementations.

---

## events.js

Responsible only for wiring UI events.

Contains:

* bindEvents()
* click handlers
* keyboard handlers
* modal bindings

No business logic.

---

## refresh.js

Responsible for server refresh.

Contains:

* refresh()
* renderPayload()

Everything involving refreshing statistics belongs here.

---

## players.js

Responsible for player handling.

Contains:

* normalizePlayers()
* extractPlayers()
* getPlayerId()
* getPlayerNickname()
* renderPlayers()
* showPlayers()

Everything involving online players belongs here.

---

## logs.js

Responsible for logs.

Contains:

* showLog()
* updateLogCounts()

Later this module will likely gain:

* pagination
* filtering
* searching

---

## actions.js

Contains all administrator actions.

Examples:

* Kick
* Ban
* Unban
* Announcement
* Shutdown
* Save World
* Emergency Stop
* Start API

This module should eventually contain every API action.

---

## configuration.js

Responsible only for server configuration.

Contains:

* add server
* edit server
* delete server
* configuration modal

---

## utils.js

Contains shared helpers.

Examples:

* getValue()
* setText()
* getPlayerCount()
* getUniqueGuildCount()

Utility functions only.

POST   /api/servers

# Coding Style

Project conventions:

* ES6
* async/await
* no frameworks
* no build step
* browser-native JavaScript
* one responsibility per module
* avoid global utility functions unless shared
* feature logic belongs inside feature modules

---

# Design Philosophy

The project intentionally favors:

* readability
* maintainability
* explicit code

over

* clever abstractions
* excessive DRY
* compact one-liners

Future contributors should preserve this style.

---

# Backend Status

The backend is currently functional but remains largely contained within a single `app.py` file (1300+ lines).

It provides the REST API consumed by the frontend and contains:

- API endpoints
- server management
- RCON communication
- configuration handling
- map generation
- process management
- various utility functions

The next major milestone is separating these responsibilities into route modules and reusable services to mirror the frontend architecture.

---

# Suggested Next Steps (Priority Order)

0. Refactor Backend Architecture (Critical)

The backend has grown to over 1300 lines and should be modularized before additional feature work.

Targeted Backend Architecture:

backend/
│
├── app.py                 # Flask startup only
│
├── routes/                # Flask Blueprints organized by feature
│   ├── status.py
│   ├── players.py
│   ├── server.py
│   ├── configuration.py
│   ├── logs.py
│   ├── map.py
│   └── admin.py
│
├── services/
│   ├── rcon.py
│   ├── process.py
│   ├── parser.py
│   ├── config.py
│   ├── cache.py
│   └── updater.py
│
├── models/
│   ├── server.py
│   └── player.py
│
├── utils/
│   ├── validation.py
│   ├── helpers.py
│   └── logging.py
│
└── extensions.py

Goals:

Keep app.py under ~200 lines.
Move each REST endpoint into feature-based route modules.
Extract business logic into reusable services.
Separate HTTP handling from server management logic.
Improve maintainability and reduce merge conflicts.
Mirror the frontend's modular architecture.

## 1. Add Toast Notifications (High Priority)

Replace silent success/failure behavior with a consistent notification system.

Examples:

* "World saved."
* "Player banned."
* "Announcement sent."
* "Shutdown scheduled."
* "API unavailable."
* "Server configuration saved."

A lightweight `ToastService` would improve feedback throughout the dashboard.

---

## 2. Implement Loading States (High Priority)

Prevent duplicate submissions and improve responsiveness by showing loading states while API calls are in progress.

Examples:

* Disable buttons during requests.
* Show spinners or "Saving...", "Sending...", etc.
* Re-enable controls after completion.

---

## 3. Centralize Error Handling (High Priority)

Many modules currently use:

```javascript
catch (error) {
    console.error(error);
}
```

Introduce a shared error handler (e.g., `ErrorService`) to:

* Log errors consistently.
* Display user-friendly messages.
* Detect API connectivity issues.
* Trigger the API unavailable modal when appropriate.

---

## 4. Move Admin Commands into Dedicated Modules (Medium Priority)

As the dashboard grows, split `actions.js` further by responsibility:

```
modules/
    admin/
        playerActions.js
        serverActions.js
        announcements.js
        shutdown.js
```

This keeps each file focused and prevents `actions.js` from becoming another large file.

# Long-Term Vision

The long-term goal is to provide a polished, maintainable administration console that exposes the full capabilities of the Palworld Dedicated Server REST API while remaining easy to extend.

The emphasis should remain on:

* **Predictable, modular backend architecture**
* **Clear module boundaries**
* **Explicit, readable JavaScript**
* **Minimal dependencies**
* **Native browser APIs**
* **Incremental feature growth without creating large, monolithic files**

By continuing to split functionality by feature and keeping services focused, the dashboard should remain approachable for new contributors and straightforward to maintain as new administrative capabilities are added.
